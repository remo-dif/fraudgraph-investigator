# Phase 1A independent review

**Verdict: REQUEST CHANGES.** The intended Compose layout separates the stores, but startup does not authenticate the datastore role before writes. The schema bootstrap also accepts constraint names without validating their definitions. Both affect Phase 1A's persistence foundation. There is no customer-data intake or import HTTP write surface in this commit.

Reviewed `feature/phase-1a-persistence-foundation` at `027c2166c916688d4ff61eeef6dd265a03544425` against `main` at `2b7e3528df01d9e035af0660faba03c10a9e759d`. The checkout matched HEAD, the initial worktree was clean, and the supplied base was the merge base. Reviewed the full 42-file diff, repository instructions, README, architecture reconciliation, ADRs 0001–0005, MVP roadmap/status, and test strategy. Java references below are relative to `backend/src/main/java/com/fraudgraph/investigator/` unless otherwise indicated. `IT` means `backend/src/test/java/com/fraudgraph/investigator/dataset/DatasetFoundationIntegrationTest.java`.

## Findings

### P1A-01 · High · Merge-blocking — Startup can write to the wrong Neo4j instance

- **Evidence:** `config/RuntimeProfiles.java:12–19` enforces exclusive profiles. `dataset/ImportPersistenceConfiguration.java:15–28` validates presence and rejects one default password before creating a driver and running schema initialization. `dataset/DatasetFoundation.java:26–40` issues DDL to that driver. `backend/src/main/resources/application-demo.yml:1–6` allows connection overrides, and `config/DataSeeder.java:13–30` performs demo initialization without verifying the target role. IT lines 38–60 use correctly wired instances and check one wrong password. IT lines 122–129 check blank properties and both profiles. ADR 0002 lines 5–9 call for separate endpoints and fail-closed operation.
- **Impact:** With valid but misdirected configuration, an import app can initialize schema on a demo or unrelated instance, and a demo app can connect to the imported store and use unscoped demo queries or seeding. The ordinary two-project Compose layout reduces this risk. These are configuration-bound consequences, not an observed leak or an HTTP attack path.
- **Correction:** Bind deployments to independently provisioned, role-specific datastore identities. Verify the expected role and identity before DDL, seeding, or route readiness. Restrict the effective endpoint and network to the intended service. Do not let either application bootstrap its own trust marker on an arbitrary reachable datastore.
- **Acceptance:** Both correct profiles boot on their designated instances. On disposable fixtures, both reversed pairings with valid credentials fail before schema/data changes. Unknown/unmarked targets and absent, invalid or default import settings fail closed. Assert the wrong store remains unchanged.

### P1A-02 · High · Merge-blocking — Constraint names are treated as proof of schema

- **Evidence:** `dataset/DatasetFoundation.java:26–40` uses named `CREATE CONSTRAINT … IF NOT EXISTS` without checking type, label or ordered properties. Neo4j can skip creation if another constraint already uses the same name. IT lines 64–73 check names and one online index. The duplicate at IT lines 79–83 can fail at DatasetVersion creation before testing Event uniqueness. [Neo4j 5 constraint creation behavior](https://neo4j.com/docs/cypher-manual/5/constraints/create-constraints/)
- **Impact:** Incompatible existing schema can pass startup and leave intended identities unenforced. The concurrent-write guarantees depend on those identities. A repeated create through the production entry point cannot isolate which constraint fired.
- **Correction:** Validate actual uniqueness constraint signatures and supporting indexes as a startup postcondition. Fail closed on incompatible definitions. Independently exercise each key in an integration fixture and validate missing mandatory values at the application boundary, consistent with Community property uniqueness semantics.
- **Acceptance:** Clean initialization and rerun both verify the exact three definitions and online backing indexes. An incompatible same-name schema is rejected. Direct duplicate fixtures prove Dataset, DatasetVersion and Event constraints independently. Invalid inputs cover each required identity and metadata component, and rejection leaves no persisted graph or links.

### P1A-03 · Medium · Merge-blocking — Scoped persistence assertions miss important branches

- **Evidence:** `dataset/DatasetFoundation.java:44–50,61–81,87–115` derives scope from the security context, revalidates the actor, checks ownership/active state inside the write transaction, and binds the actor, dataset, version, relationship scope and event key on read. IT lines 74–119 exercise no principal, wrong owner, stale scope, wrong endpoints and injected pre-commit rollback. Identical event payloads are written to all valid scopes. Tests inject mismatched endpoints but do not independently test mismatched relationship metadata, and they never run concurrent transactions or an authenticated principal lacking the internal authority.
- **Impact:** Existing assertions can miss regressions in scope selection, relationship metadata or authorization. A duplicate sequential write does not establish that competing writes leave one consistent graph.
- **Correction:** Use differing sentinel payloads under overlapping external IDs and assert the selected dataset/version. Add tests for relationship metadata, wrong authority, lifecycle states and competing foundation writes. Keep full CSV retry idempotency and deletion in Phase 1B.
- **Acceptance:** Positive reads distinguish both versions and both owners. Independently verify relationship and endpoint mismatch exclusions for both hops, missing or wrong authority denial, and disabled lifecycle states. Concurrent foundation creates leave one consistent version/event graph and no orphan relationships. The injected failure still yields zero rows, and duplicate or database failures return sanitized errors.

### P1A-04 · Medium · Phase 1B gate — Creation semantics must stay off public routes

- **Evidence:** `dataset/DatasetFoundation.java:44–50,63–79` accepts an internal caller's dataset ID, merges the Dataset, assigns the current actor on creation and denies a foreign existing owner. Reading both a missing and a foreign dataset yields empty in IT lines 96–101. `dataset/PreviewSecurity.java:63–69` denies all import HTTP. ADR 0002 lines 7–9 requires equivalent absent and inaccessible responses.
- **Impact:** Exposing the current method through a user-controlled dataset ID would make first creation versus an existing foreign dataset distinguishable. This is an internal fixture API today. Authentication in the test is synthetic and does not establish issuer or subject validation by an HTTP provider.
- **Correction:** Before wiring a caller-facing import flow, separate server-generated dataset creation from adding a version under existing ownership. Define stable trusted actor-key mapping and consistent denial before responding. Preserve the explicit transactional owner check.
- **Acceptance:** Client-supplied IDs cannot claim a new dataset. Adding a version to missing or inaccessible scope yields the same public response and no writes. Unauthenticated and non-owner requests cannot create a version under an existing dataset. This is not a Phase 1A merge blocker while import routes remain closed.

### P1A-05 · Medium · Merge-blocking — Required test execution needs stronger evidence

- **Evidence:** `backend/build.gradle:30–46` separates tests and rejects zero/skipped tests through an `afterSuite` callback. A task that resolves to `NO-SOURCE` may never invoke that callback. `.github/workflows/ci.yml:64–85` checks Docker and runs the integration task before demo smoke. `docs/testing.md:3–14` calls for a required ruleset check. The workflow has no independent execution/report assertion. Hosted required-check configuration was not established by the review.
- **Impact:** A configuration or source-set regression could leave no result to evaluate. Local execution alone does not establish that the merge gate is required or passed on the reviewed SHA.
- **Correction:** Add CI-side evidence that the mandatory integration class produced fresh nonempty passing results and publish its report. Require the hosted status check and record current-SHA CI and demo smoke outcomes. Wait for completed seeding and assert a nonempty seeded case graph. Generic actuator health can report UP while the startup runner is still populating the demo.
- **Acceptance:** CI fails on absent integration sources/results, missing Docker, skipped/failing tests and normal test failures. A fresh reviewed-SHA run publishes reports and the required status check is enforced. Demo smoke preserves expected dashboard and case hypergraph behavior.

### P1A-06 · Low · Non-blocking — Status documentation mixes implementation and historical verification

- **Evidence:** `docs/mvp-status.md:3–15` describes Phase 1A as implemented while retaining the older source baseline and listing the same capabilities as planned. Its passing-test claim refers to a working tree. `README.md:155–156,171,188` both provides the suite and describes adding one as future work.
- **Impact:** Readers can overstate independent proof or miss the distinction between an internal test identity and a pilot identity provider.
- **Correction:** Reconcile the status table with implemented, independently verified, blocked, and later-phase items. Attach test claims to the exact SHA and distinguish local, hosted and synthetic verification.
- **Acceptance:** README and status agree on what exists and what passed, with open merge and customer-data gates explicit.

## Remaining risks and corrective order

1. Require datastore identity and an exact schema contract before accepting writes.
2. Strengthen the scope and constraint assertions, then require fresh CI evidence and demo smoke for the corrected SHA.
3. Align status documentation and preserve the Phase 1B and pilot gates. Import uses the same bootstrap/runtime admin credential in the development stack. Network separation relies on separate Compose projects as documented in README. The demo's baseline published ports remain development-only. An approved pilot still needs identity issuance, least-privilege or documented Community compensating controls, private ingress, retention and recovery, and measured resource limits. Actual pilot network and trust settings remain unverified. Before expanding the import context, assert absence of all legacy routes and repositories, including the unchanged Spring Data `repository/CaseRepository.java:6`, whose auto-registration in import is not explicitly gated in this diff.
